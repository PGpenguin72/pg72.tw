# Challenge Minecraft???

> I placed a lectern near this village. There is a book inside, but I definitely did not hide the Flag there :D
>
> Goal: Find the lectern shown in the image. Once you reach it, you will definitely find the Flag…?

The challenge provides a Minecraft screenshot and asks us to find the lectern shown in it. The server runs Java `1.21.11`, and the search range is:

```text
X: 100000 ~ 150000
Y: 60 ~ 75
Z: -1000 ~ 1000
```

![The lectern from the challenge](./asset/chal.png)

At first, this looks like a problem that requires exploring the server manually. However, the hint explains that block patterns in the screenshot can be used to recover the coordinates. The actual solution is to use Minecraft texture rotations as a location fingerprint.

# Core idea: block textures are not always fixed

## Coordinate-dependent random textures

Some Minecraft block textures are not rendered with exactly the same orientation at every position. The game applies a reproducible pseudo-random result based on the block position and the rendering implementation, so large areas do not look completely repetitive.

This is not cryptographically secure randomness. Under the same Minecraft version and rendering mode, the same coordinates produce the same texture rotation result. That makes the visual pattern useful as a fingerprint.

If we record the following information from the screenshot:

- the relative position of each observed block;
- its texture rotation number;
- its side-flip state when necessary;

we can search the given coordinate range for locations that produce the same pattern.

That is why a screenshot can leak a location even when the F3 screen and XYZ coordinates are not visible.

## This is not seed cracking

This challenge does not first recover the Minecraft world seed and then search the world.

More precisely, the tool compares the texture-rotation pattern extracted from the screenshot with the expected result for every candidate coordinate in the configured range. A matching location is returned as a candidate coordinate.

The important input is therefore not a complete map, but an origin block plus the relative positions and rotations of the other blocks.

# The TextureRotations tool

The tool used in this challenge is [19MisterX98/TextureRotations](https://github.com/19MisterX98/TextureRotations). It is a texture-rotation reverser that supports Vanilla and Sodium modes and uses multiple threads to speed up the search.

The project provides two resource packs:

1. [Manual texture rotations](https://github.com/19MisterX98/TextureRotations/releases/download/1/Manual_texture_rotations.zip)
2. [Textures to numbers](https://github.com/19MisterX98/TextureRotations/releases/download/1/Textures_to_numbers.zip)

## Manual texture rotations

This resource pack replaces blocks with visually obvious directional textures. It allows a solver to inspect the screenshot and identify the rotation more easily.

The project README gives examples of these replacements:

## Textures to numbers

The second resource pack overlays the rotations with numbers. Instead of describing a direction manually, we can record a value such as `0`, `1`, `2`, or `3` and pass it to the tool.

The two resource packs therefore have different roles:

```text
Manual texture rotations  ->  make the rotations easy to inspect
Textures to numbers        ->  convert the rotations into program input
```

The challenge does not provide a prepared JSON file. In the actual solve, I used the resource packs to recreate the terrain from the screenshot, read the rotation states from that reconstruction, and then organized the observations into a format that the tool could use.

# Reconstructing the terrain from the screenshot

I first used the `Manual texture rotations` resource pack to replace blocks with textures whose directions were easy to identify. Then I rebuilt a small section of the terrain in Minecraft. Recreating the entire village was unnecessary; the important part was preserving enough blocks with clear relative positions.

The screenshot orientation also matters. The challenge states that the lectern faces positive Z and that its left side points toward positive X. I used this as the coordinate reference while rebuilding the scene and drew lines to mark the relative positions between blocks.

![Reconstructed terrain with manually marked positions](./asset/0.png)

The lines in this image were drawn by me while solving the challenge. They were not part of the original challenge files. They helped me identify the direction of each block relative to the origin and avoid swapping or mirroring the X/Z axes.

# Manually preparing the tool input

After reconstructing the scene, I read the rotation number shown by the resource pack for each block and recorded its position relative to the origin. The input concept is approximately:

```json
{
  "pos": {
    "x": 0,
    "y": 0,
    "z": -1
  },
  "rotation": 0,
  "side": false
}
```

The fields mean:

| Field | Meaning |
| --- | --- |
| `pos.x` | X offset from the origin block |
| `pos.y` | Y offset from the origin block |
| `pos.z` | Z offset from the origin block |
| `rotation` | Rotation number read from the numbered resource pack |
| `side` | Whether only the side-flip state is known |

For example:

```json
{
  "pos": {
    "x": 1,
    "y": 0,
    "z": 0
  },
  "rotation": 1,
  "side": true
}
```

means that the block is one block in the positive X direction from the origin, has state `1`, and only its side state is known.

The origin must be consistent for every observation. Bedrock and Stone can have two side states; when only the side state is known, `side` should be `true`. Other supported blocks mainly use top or bottom rotations.

## Coordinate orientation matters

Relative coordinates do not automatically tell us how the screenshot is oriented. Mirroring the image or swapping the X/Z directions can make every individual observation look valid while causing the whole fingerprint to fail.

The challenge gives the required orientation: the lectern faces positive Z, and its left side points toward positive X. This lets us construct the relative coordinates without accidentally mirroring the input.

# Solving the challenge

## 1. Reconstruct the terrain and record observations

Use the resource pack to recreate the terrain from the screenshot. After confirming the orientation, choose one block as the origin and record the X, Y, and Z offsets and rotation number of the other blocks.

![Building the texture-rotation pattern](./asset/1.png)

The recorded data is not a complete Minecraft building. It is a compact fingerprint containing relative positions and texture rotations. A sufficiently distinctive group of observations is enough to reduce the search space.

## 2. Select the correct version mode

This step matters because Minecraft has changed its random-number implementation across versions, and Sodium has also used different implementations.

According to the TextureRotations README:

| Minecraft version | Vanilla mode |
| --- | --- |
| `<= 1.12.2` | `Vanilla12Textures` |
| `1.13 ~ 1.21.1` | `Vanilla21_1Textures` |
| `1.21.2+` | `VanillaTextures` |

The server in this challenge is Java `1.21.11`, so we should select `VanillaTextures`, the mode for `1.21.2+`, rather than `Vanilla21_1Textures`.

Using the wrong mode may produce no results or apparently valid but incorrect coordinates.

## 3. Set the search range

Enter the range from the challenge:

```text
X Min: 100000
X Max: 150000
Y Min: 60
Y Max: 75
Z Min: -1000
Z Max: 1000
```

The tool checks candidate positions in this three-dimensional range, calculates the expected rotations, and compares them with the observations manually extracted from the reconstructed terrain.

The range contains more than 1.6 billion possible positions: 50,001 X values, 16 Y values, and 2,001 Z values. This is why multithreading is useful, and why both the search range and the number of observations matter.

## 4. Inspect the candidates

The tool returns many matching coordinates, such as:

```text
117346 71 -980
138775 67 -976
121780 65 -972
107175 62 -968
100839 63 -962
...
114330 61 90
143140 66 90
128696 75 113
...
```

Multiple results do not necessarily mean that the tool failed. It means that this texture fingerprint still has collisions in the selected range. More observations, a smaller range, or environmental clues can reduce the candidates further.

One result is particularly suspicious:

```text
114514 72 810
```

`114514` is a very recognizable meme number, and `72` also matches the page number of the book that contains the Flag. This is clearly the intended coordinate.

# Limitations and practical notes

This technique does not work on every screenshot. The main limitations are:

1. The screenshot must contain enough blocks with supported rotation information.
2. The Minecraft and Sodium versions must be known or correctly inferred.
3. The X/Z orientation must not be mirrored or swapped.
4. The resource-pack numbering and the tool's rotation model must match.
5. The tool does not support every block; its README explicitly notes that netherrack is unsupported.

Candidate collisions are also normal. In a real investigation, we would use more block samples, narrow the coordinate range, or compare the surrounding terrain and structures to confirm the final location.

# Summary

The complete process is:

1. Inspect block textures and rotations in the screenshot.
2. Use `Manual texture rotations` to make orientations easy to identify.
3. Use `Textures to numbers` to convert rotations into numeric observations.
4. Record relative coordinates and rotations around a consistent origin.
5. Enter the manually recorded relative coordinates and rotations, then select the correct Minecraft version mode.
6. Configure the X, Y, and Z search ranges.
7. Identify `114514 72 810` among the candidates.
8. Teleport there and read the book.

This is a Minecraft example of information leakage: an ordinary game screenshot may reveal the location of a base. Hiding the F3 screen is not always enough—the blocks themselves may give the location away :D
